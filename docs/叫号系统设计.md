# 叫号系统设计

> 状态：方案设计，当前暂不开发。
>
> 本文用于约束后续叫号系统的业务边界、角色、数据模型和演进路线。正式开发前应根据实际场景补充设备协议、租户隔离和部署容量评估。

## 1. 建设定位

叫号系统面向需要排队、窗口办理和现场调度的服务场所，解决以下问题：

- 让办事人员能够按业务取号、预约和查询排队进度。
- 让窗口工作人员能够按规则呼叫、办理和结束号码。
- 让现场管理人员能够实时处理拥堵、优先号和异常号码。
- 让运营管理人员能够统计等待时长、办理时长和窗口服务效率。

叫号系统属于业务能力，不应直接堆积到工作台或平台全局配置中。按照 [`docs/系统架构.md`](系统架构.md) 的模块边界，后续应作为独立业务模块接入 `middle_platform`。

## 2. 与平台的边界

### 2.1 平台提供的能力

叫号模块复用平台已有能力：

- 用户、组织、租户和 Session。
- 权限组、权限码和路由守卫。
- 工作台入口、控制台分类和单点登录。
- 通用系统配置、文件能力和操作审计。
- API 入口、CSRF、限流和错误处理。

### 2.2 叫号模块负责的能力

叫号模块独立负责：

- 业务分类、服务窗口和排队规则。
- 排队号码、预约记录和号码状态流转。
- 工作人员叫号台、现场调度和异常处理。
- 大屏展示、语音播报和设备适配。
- 等待时长、办理时长和服务效率统计。

模块不得直接读取其他业务模块的数据表；跨模块访问通过平台公开服务或版本化 API 完成。

## 3. 目标角色

### 3.1 办事人员

- 现场取号或预约取号。
- 选择业务分类和服务事项。
- 查询当前号码、前方等待人数和预计等待时间。
- 接收叫号提醒，处理取消、过号和重新排队。

### 3.2 窗口工作人员

- 登录并绑定服务窗口。
- 开始、暂停和恢复窗口服务。
- 呼叫下一位、重复呼叫和过号。
- 标记办理中、办理完成或转移业务。

### 3.3 现场调度人员

- 查看所有业务和窗口的实时队列。
- 调整窗口承接的业务分类。
- 处理优先号、插入号码、转移号码和异常号码。
- 临时开启、关闭或合并窗口。

### 3.4 运营管理人员

- 查看等待量、办理量和服务效率。
- 按日期、业务、窗口和工作人员筛选报表。
- 导出统计结果，分析高峰时段和服务瓶颈。

### 3.5 系统管理员

- 管理叫号模块用户权限。
- 配置业务分类、窗口、规则、通知和设备。
- 管理模块参数、字典和审计策略。

## 4. 功能范围

### 4.1 基础配置

- 业务分类：编码、名称、优先级、启停状态、服务时段。
- 服务事项：事项名称、所属分类、所需材料和办理说明。
- 服务窗口：窗口编号、名称、位置、状态和支持业务。
- 工作人员：平台用户与窗口、业务分类的绑定关系。
- 排队规则：普通号、预约号、优先号、最大等待时长和过号规则。
- 节假日和营业时段：按日期配置可服务时间。

### 4.2 取号与预约

- 现场取号：选择业务后生成排队号码和取号凭证。
- 预约取号：选择日期、时间段和业务事项。
- 多渠道取号：前台、取号机、二维码、手机端或外部系统。
- 取号限制：同一用户重复取号、每日次数和预约冲突校验。
- 号码展示：号码、业务、前方人数、预计等待时间和当前状态。

### 4.3 窗口叫号台

- 查看当前窗口队列和下一位候选号码。
- 呼叫下一位、重复呼叫、过号、暂停和恢复。
- 开始办理、完成办理、取消办理。
- 转移到其他业务或窗口。
- 记录办理备注和异常原因。

### 4.4 调度中心

- 查看各分类、窗口和队列的实时状态。
- 手动调整队列顺序，但必须记录操作原因和操作人。
- 插入优先号码或特殊保障号码。
- 临时调整窗口业务范围和工作人员。
- 对超时、无人响应和设备离线状态进行处理。

### 4.5 大屏与语音

- 展示当前叫号、窗口号和最近叫号记录。
- 支持按区域、业务分类或大厅配置多个展示屏。
- 语音播报号码、窗口和办理事项。
- 配置播报次数、音量、语言、声音和播报模板。
- 支持公告、通知和宣传内容轮播。

### 4.6 通知与评价

- 到号前提醒和叫号提醒。
- 支持站内消息、短信、公众号或其他外部通知适配器。
- 办理完成后发起服务评价。
- 记录评价结果和投诉建议，并支持后续统计。

### 4.7 统计与审计

- 取号量、办理量、完成量、取消量和过号量。
- 平均等待时长、平均办理时长和最长等待时长。
- 按业务分类、窗口、工作人员、日期和时段统计。
- 记录取号、呼叫、过号、转移、完成和人工调度日志。
- 支持查询、导出和权限控制，原始记录不可被普通用户修改。

## 5. 核心业务流程

### 5.1 普通取号流程

```text
选择业务分类
  → 校验营业时间和取号限制
  → 生成排队号码
  → 进入等待队列
  → 窗口按规则呼叫
  → 办事人员到窗口
  → 开始办理
  → 办理完成 / 转移 / 异常结束
```

### 5.2 预约流程

```text
选择业务和预约时段
  → 校验时段容量
  → 生成预约记录
  → 到预约时间转为待叫号
  → 按预约规则进入队列
  → 呼叫和办理
```

### 5.3 号码状态

推荐状态：

```text
WAITING       等待中
CALLED        已叫号
SERVING       办理中
COMPLETED     已完成
SKIPPED       已过号
TRANSFERRED   已转移
CANCELLED     已取消
EXPIRED       已失效
```

状态变化必须由服务端校验，不能由前端直接修改任意状态。所有状态变化记录操作人、操作时间、来源终端和原因。

## 6. 数据模型建议

以下表属于叫号模块自己的数据，不应放入平台全局表：

### 6.1 `queue_categories`

业务分类：

- `id`
- `tenant_id`
- `code`
- `name`
- `priority`
- `enabled`
- `service_start_time`
- `service_end_time`
- `created_at`
- `updated_at`

### 6.2 `queue_services`

具体服务事项：

- `id`
- `category_id`
- `code`
- `name`
- `description`
- `enabled`
- `estimated_minutes`

### 6.3 `queue_windows`

服务窗口：

- `id`
- `tenant_id`
- `code`
- `name`
- `location`
- `status`
- `enabled`

### 6.4 `queue_window_services`

窗口与服务事项的关联关系：

- `window_id`
- `service_id`
- `priority`

### 6.5 `queue_staff_assignments`

工作人员与窗口、业务的绑定关系：

- `user_id`
- `window_id`
- `category_id`
- `started_at`
- `ended_at`

### 6.6 `queue_tickets`

排队号码：

- `id`
- `tenant_id`
- `ticket_no`
- `service_id`
- `category_id`
- `source`
- `appointment_id`
- `status`
- `priority_level`
- `issued_at`
- `called_at`
- `serving_at`
- `completed_at`
- `expired_at`

### 6.7 `queue_calls`

叫号事件：

- `id`
- `ticket_id`
- `window_id`
- `staff_user_id`
- `action`
- `sequence_no`
- `reason`
- `created_at`

### 6.8 `queue_devices`

设备注册和状态：

- `id`
- `type`
- `code`
- `name`
- `location`
- `last_seen_at`

设备配置应使用受控 JSON 配置，不允许业务页面直接写入任意设备指令。

## 7. 排队规则

队列排序建议按以下优先级计算：

1. 是否为有效预约号。
2. 业务优先级或特殊保障级别。
3. 号码进入队列的时间。
4. 号码序号。

规则必须由服务端统一计算。窗口端只能请求“下一位”，不能自行从前端列表选择并修改队列顺序。

需要明确处理的异常场景：

- 叫号后无人响应。
- 多次过号后的失效策略。
- 窗口临时离线或工作人员退出。
- 业务分类暂停服务。
- 预约迟到和提前到达。
- 跨天未完成号码。
- 同一号码重复提交完成请求。

## 8. 权限设计

建议权限码使用 `queue.*` 前缀：

| 权限 | 用途 |
| --- | --- |
| `queue.read` | 查看业务、窗口和队列 |
| `queue.create` | 取号、创建预约或创建配置 |
| `queue.write` | 修改业务、窗口、规则和号码状态 |
| `queue.call` | 呼叫、重呼、过号和办理操作 |
| `queue.dispatch` | 调度队列、窗口和优先号码 |
| `queue.report` | 查看和导出统计报表 |
| `queue.device` | 管理大屏、取号机和语音设备 |
| `queue.audit` | 查看叫号操作审计 |
| `queue.unlink` | 删除配置数据 |

平台管理员可以拥有全部权限，窗口工作人员只应拥有当前窗口和授权业务范围内的 `queue.call` 权限。

## 9. 模块和接口规划

后续模块建议放置在：

```text
src/modules/queue/
server/src/modules/queue/
```

后端按以下边界拆分：

```text
route → middleware → controller → service → repository → database
```

建议接口方向：

```text
GET    /api/queue/categories
GET    /api/queue/services
GET    /api/queue/windows
POST   /api/queue/tickets
GET    /api/queue/tickets/:id
POST   /api/queue/windows/:id/call-next
POST   /api/queue/tickets/:id/recall
POST   /api/queue/tickets/:id/skip
POST   /api/queue/tickets/:id/complete
POST   /api/queue/tickets/:id/transfer
GET    /api/queue/display/:deviceCode
GET    /api/queue/reports/summary
```

接口路径仅作为设计草案，正式开发前需要根据 API 版本规范、租户上下文和权限中间件确定最终路径。

实时状态建议优先使用 SSE；当需要双向设备控制或高频状态同步时再引入 WebSocket。实时通道只推送状态变化，号码状态的最终写入仍由普通 API 和事务完成。

## 10. 分阶段建设

### 阶段一：MVP

- 业务分类和服务窗口配置。
- 工作人员登录和窗口绑定。
- 现场取号。
- 呼叫下一位、重呼、过号和完成。
- 基础大屏和语音播报。
- 基础权限、日志和统计。

### 阶段二：运营增强

- 预约取号。
- 优先号和调度中心。
- 等待时间预测。
- 短信、公众号或站内通知。
- 服务评价和投诉处理。
- 多区域、多大厅和多租户隔离。

### 阶段三：设备与服务拆分

- 取号机、打印机、LED 屏和音响适配器。
- 独立实时消息服务。
- 高并发队列和离线容错。
- 独立报表或数据分析服务。
- 在具备独立部署、扩容或团队维护需求时，再拆分为独立服务。

## 11. 当前决策

- 当前不开发叫号系统功能，不新增叫号模块代码和数据库迁移。
- 后续优先作为 `middle_platform` 的独立业务模块开发，复用平台身份、权限、工作台、SSO 和审计能力。
- 叫号模块不得把业务字段继续堆入 `dashboard_apps` 或 `system_settings`。
- 设备、实时通信和通知能力预留适配器边界，避免第一期与具体硬件协议强耦合。
