# 系统架构与 Monorepo 规范

## 1. 文档目的

本文档定义本工程面向多行业、多产品持续扩展时采用的系统架构、目录结构和协作规则。

目标业务范围包括但不限于：

- 人事管理
- 财务管理
- 供应链管理
- 教育管理
- 医疗管理
- 行业专用业务系统

本文档描述的是工程演进的标准目标。当前仓库仍处于平台基础能力建设阶段，新增功能应按本文档逐步落位，不要求一次性完成全部目录迁移。

## 2. 总体定位

本工程定位为：

> 多租户企业应用平台，由统一平台内核承载身份、权限、工作台和公共服务，由相互隔离的业务模块承载具体行业能力。

系统采用“模块化单体优先、按领域逐步拆分”的演进路线：

1. 早期使用一个仓库、一个前端壳、一个 API 服务和一个数据库集群。
2. 通过模块边界隔离平台能力与业务能力。
3. 当某个领域具备独立团队、独立发布、独立扩容或独立合规要求时，再将其拆分为独立服务。

不以微服务数量作为架构目标，优先保证业务边界、数据隔离和可演进性。

## 3. 架构分层

```text
统一入口层
├── 登录与单点登录
├── 租户/组织选择
├── 产品工作台
└── 消息、待办与通知入口

平台内核
├── 身份与租户（Identity）
├── 用户、角色与权限（IAM）
├── 产品/模块注册（Workbench）
├── 系统配置（Settings）
├── 文件中心（File）
├── 工作流（Workflow）
├── 报表中心（Report）
├── 消息通知（Notification）
├── 集成中心（Integration）
└── 操作审计（Audit）

业务模块
├── 人事（HR）
├── 财务（Finance）
├── 供应链（Supply Chain）
├── 教育（Education）
│   └── 阳光分班（Sunny Class）
└── 医疗（Medical）
```

平台内核提供跨业务复用的基础能力，业务模块拥有自己的领域模型、接口、页面、权限和数据库迁移。

在当前仓库尚未完成目录迁移前，应使用以下等价分层：

```text
src/
├── app/                          # 应用启动、路由和 Provider
├── platform/                     # 平台前端功能
├── modules/                      # 业务模块前端功能
└── shared/                       # 无业务归属的公共代码

server/src/
├── bootstrap/                    # Express 启动和模块注册
├── middleware/                   # 认证、权限、CSRF、限流、错误处理
├── platform/                     # 平台后端模块
├── modules/                      # 业务模块后端
├── db/                           # 连接池、迁移和事务工具
└── shared/                       # 公共错误、日志、校验和工具
```

## 5. 模块标准

每个业务模块必须拥有清晰的边界，推荐使用以下结构：

```text
modules/<module-key>/
├── frontend/
│   ├── pages/
│   ├── components/
│   ├── hooks/
│   ├── api.ts
│   ├── types.ts
│   ├── routes.tsx
│   └── index.ts
├── backend/
│   ├── routes.js
│   ├── controller.js
│   ├── service.js
│   ├── repository.js
│   ├── validator.js
│   └── index.js
├── migrations/
├── permissions.ts
└── README.md
```

模块入口 `index` 负责向平台注册路由、菜单、工作台产品、权限和事件；模块内部实现细节不得由其他模块直接引用。

平台模块也遵守同样的边界规则，例如 `platform/identity`、`platform/iam` 和 `platform/workbench` 不应继续把所有逻辑集中在单一入口文件中。

## 6. 依赖与边界规则

### 6.1 允许的依赖方向

```text
app/bootstrap
    ↓
platform / modules
    ↓
shared / packages
```

- `app` 或 `bootstrap` 可以注册平台模块和业务模块。
- 业务模块可以调用平台公开服务和公共包。
- 平台模块可以调用 `shared` 和公共包。
- `shared`、公共包不得依赖具体业务模块。

### 6.2 禁止的依赖

- 业务模块不得直接读取其他模块的数据库表。
- 业务模块不得直接修改其他模块的数据迁移。
- 页面不得绕过模块 API 直接拼接业务请求。
- Controller 不得承载复杂业务规则、事务编排或算法实现。
- `system_settings` 不得继续堆放人事、财务、教育等业务配置。
- 不得通过复制代码的方式创建相似模块；应提取到公共包或平台服务。

跨模块协作只能通过以下方式进行：

1. 平台公开服务接口。
2. 版本化 API。
3. 明确的事件契约。
4. 经过评审的只读查询接口。

## 7. 前端规范

统一前端壳负责：

- 登录态恢复和退出登录。
- 租户、组织和当前用户上下文。
- 全局布局、导航和工作台。
- 权限菜单过滤和路由守卫。
- 全局错误、通知和主题配置。

业务模块负责：

- 自己的页面、表单、表格和业务组件。
- 自己的 API 客户端和 TypeScript 类型。
- 自己的路由注册和权限声明。
- 自己的加载、错误、空数据和无权限状态。

路由统一使用模块前缀，例如：

```text
/education/sunny-class/students
/education/sunny-class/plans
/finance/vouchers
/hr/employees
```

全局路由文件只做路由组合，不写具体业务页面实现。

## 8. 后端规范

后端请求链路统一为：

```text
route → middleware → controller → service → repository → database
```

- `route`：声明 HTTP 方法、路径和中间件。
- `middleware`：处理认证、权限、参数预处理和限流。
- `controller`：转换 HTTP 请求和响应，不实现领域规则。
- `service`：实现业务规则、事务和跨服务编排。
- `repository`：封装本模块的数据读写。
- `database`：提供连接、迁移和事务基础设施。

API 使用版本和模块前缀：

```text
/api/v1/auth/login
/api/v1/workbench/apps
/api/v1/education/sunny-class/students
/api/v1/finance/vouchers
```

## 9. 多租户与权限

平台面向多个企业、学校、医院或集团时，核心业务数据必须具备租户隔离能力。

业务表原则上包含：

```text
tenant_id
organization_id
created_by
updated_by
created_at
updated_at
```

权限采用 RBAC 与数据范围结合的方式，权限编码使用稳定的资源动作格式：

```text
hr.employee.read
hr.employee.write
finance.voucher.approve
education.sunny_class.plan.publish
medical.patient.view_sensitive
```

后端必须执行最终权限校验，前端权限只用于菜单、按钮和交互提示，不能作为安全边界。

财务和医疗等敏感领域还应支持组织范围、数据范围和字段级敏感权限。

## 10. 数据库与迁移

数据库按平台和业务领域隔离。推荐使用 PostgreSQL schema 或等价的模块迁移目录：

```text
platform.users
platform.roles
platform.tenants
hr.employees
finance.vouchers
education.students
education.sunny_class_plans
medical.patients
```

迁移文件必须可重复执行、可审计、按序编号，例如：

```text
001_create_platform_tables.sql
002_add_sso_ticket.sql
003_create_sunny_class_tables.sql
004_add_rbac.sql
```

应用启动时不再依赖散落在业务入口中的大段 `CREATE TABLE` 和临时 `ALTER TABLE`。数据库变更必须通过迁移完成，并在文档中说明兼容性和回滚策略。

## 11. 工作台与产品注册

工作台同时支持内部模块和外部系统，产品注册信息至少包含：

```text
code
name
kind: internal | external
module_key
entry_url
icon
enabled
sort_order
tenant_scope
required_permissions
version
```

- `internal`：进入本仓库注册的前端业务模块。
- `external`：通过 URL、SSO 或其他集成方式访问外部系统。
- 产品是否显示由租户、用户角色、权限和启用状态共同决定。

## 12. 质量与交付要求

每个模块至少应具备：

- 模块 README，说明职责、入口、依赖和数据表。
- API 类型或接口文档。
- 关键业务规则的单元测试。
- 数据迁移和初始化数据说明。
- 权限清单。
- 重要操作的审计记录。

提交代码前应完成与改动范围匹配的检查：

```bash
npm run build
(cd server && npm test)
```

引入新模块时必须同时更新工作台注册、权限、路由、数据库迁移、测试和相关文档，不能只提交页面代码。

## 13. 演进路线

### 阶段一：模块化单体

保留当前 React/Vite + Express + PostgreSQL 技术栈，先拆分入口文件、路由、服务、仓储和迁移，建立 `platform` 与 `modules` 边界。

### 阶段二：异步任务

将 Excel 导入、报表生成、批量计算、文件处理、消息发送和复杂算法迁移到 `worker`，避免长时间占用 API 请求。

### 阶段三：领域服务拆分

当某个领域满足独立团队、独立部署、独立扩容或独立合规要求时，再拆分为独立服务。统一身份、权限、网关和工作台仍由平台层提供。

微前端同样延后到确有独立发布和技术栈隔离需求时再引入，不能作为初始目录设计的前提。

## 14. 当前仓库的落地顺序

1. 将 `server/src/index.js` 拆为启动、公共中间件、平台路由和业务路由。
2. 将 `src/App.tsx` 改为统一路由注册器。
3. 将 `src/api.ts` 拆为平台 API 和模块 API。
4. 引入 `/api/v1`，保留必要的兼容重定向或兼容接口。
5. 将数据库初始化迁移到正式 migration 机制。
6. 建立租户、组织、角色、权限模型。
7. 以阳光分班作为第一个完整业务模块验证规范。
8. 根据实际负载再引入 worker 或独立领域服务。

任何新增行业功能都必须先确定其所属领域、数据边界、权限边界和平台依赖，再确定代码目录。

## 15. 当前适配状态

本仓库已完成第一阶段的低风险适配：

- 前端新增 `src/app/routes.tsx`，统一组合平台路由和业务模块路由。
- 前端新增 `src/modules/registry.ts`，提供业务模块路由注册点。
- 现有 SSO 已按平台模块落位于 `server/src/platform/sso`，包含路由、控制器、服务、仓储、Ticket 工具和测试。
- 后端新增 `server/src/bootstrap/module-registry.js`，按公共路由和受保护路由两个阶段注册平台模块，并预留业务模块注册点。
- 前端公共请求能力已落位于 `src/shared/api-client.ts`，SSO API 和类型已落位于 `src/platform/sso`。
- 数据库迁移已具备 `server/src/db/migrate.js` 和 `server/src/db/migrations/` 基础。

当前仍保留在旧入口中的工作台、用户和系统配置逻辑，属于后续拆分范围。后续拆分必须保持现有功能和部署兼容，并按“路由 → 控制器 → 服务 → 仓储 → 数据库”的链路逐步迁移。新增第一个行业模块时，应同时创建前端模块、后端模块、迁移、权限清单、测试和模块 README。
